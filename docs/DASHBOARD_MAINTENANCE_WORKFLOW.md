# Dashboard Maintenance Workflow

## Purpose

This document explains the exact workflow used to create, update, and validate the Watchout Recommendations Dashboard in this repository.

The dashboard is delivered as a self-contained HTML output generated from a template and local CSV/JSON files.

---

The dashboard consists of:

1. A single application file:
- dashboard_watchout_recommendations_embedded.html

Template source:
- tools/templates/dashboard_watchout_recommendations.template.html

- data/runtime/heatmaps/BMW_Watchouts.csv

## How the Dashboard Was Created

### 1. Create the base application

The dashboard template is maintained in tools/templates/dashboard_watchout_recommendations.template.html with:

- HTML for layout
- CSS for styling
- JavaScript for data loading, filtering, decision-tree execution, and CSV export

### 2. Load local data files

The HTML uses Fetch plus Papa Parse to load CSV files and JSON lookups from the local workspace.

### 3. Build in-memory lookup maps

At startup, the JavaScript builds lookup maps for:

- organic web conversion
- paid web conversion
- High Value NVWR share
- Cost per NVWR
- media mix paid share
- total media cost
- IWVV to IWVV Paid ratio
- NSC Prospects actual versus benchmark
- model-to-series mapping

These maps are used by the decision tree so each row can be evaluated quickly.

### 4. Restrict the analysis to topsellers

The dashboard only evaluates market-model-drivetrain combinations that are included in data/runtime/config/topsellers_per_market.json.

That file is generated from source/BMW_BG26-OI-R.csv using the 70 percent budget coverage rule.

## How to Update the Dashboard

### A. Update UI or layout

Edit tools/templates/dashboard_watchout_recommendations.template.html when changing:

- labels and language
- table layout
- filter controls
- export column names
- styling

Examples of recent UI changes:

- German to English translation
- multiselect dropdown filters with checkboxes
- status text cleanup

### B. Update decision-tree logic

Edit tools/templates/dashboard_watchout_recommendations.template.html when changing:

- decisionA()
- decisionB()
- decisionC()
- decisionD()
- supporting watchout detection functions
- KPI threshold checks

Typical process:

1. Find the relevant decision function.
2. Change the branching logic.
3. Update the recommendation text.
4. Keep decision-path labels aligned to the business rule names.
5. Validate that dependent helper functions still match the rule.

Examples of recent logic changes:

- Sales watchout changed to SALES < 0 only
- Node C reordered to C.1 -> C.2 -> C.3 -> C.4, with C.2 using CRM-specific 3-month duration and the Sales-or-risk condition
- Node D now blocks recommendations when prediction is a chance
- Node A now follows the updated A.1, A.2, A.3, A.4, A.10 flow, with A.3 triggered by either Sales watchout plus not-chance or explicit risk
- CS web conversion now uses regional aggregation across AT, BG, CZ, GR, HU, PL, RO, SI, SK
- CS Cost per NVWR and Paid Share now use regional aggregation across the same CS country set

### C. Update source data

If the business wants refreshed data rather than logic changes:

1. Replace the source-managed files in `source/` (including `BMW_Watchouts.csv` and `BMW_BG26-OI-R.csv`) and any direct runtime-only inputs.
2. Regenerate derived files (including runtime clean web CSVs, media JSONs, topsellers, and MSF ratio lookups).
3. Rebuild the embedded dashboard.
4. Reload the dashboard.
5. Re-export outputs.

### D. Regenerate derived files

Use the PowerShell scripts in the repository when relevant:

1. tools/analyze_topsellers.ps1
   - regenerates data/runtime/config/topsellers_per_market.json

2. tools/build_msf_in_iwvv_ratio.ps1
   - regenerates data/runtime/media/msf_in_iwvv_ratio.json

3. tools/build_media_runtime_jsons.ps1
   - regenerates media lookups from source/BMW_Media_C1.xlsx:
   - data/runtime/media/cost_per_nvwr_paid.json
   - data/runtime/media/media_mix_paid_share.json
   - data/runtime/media/media_total_cost.json
   - data/runtime/media/cs_paid_webconversion.json

4. tools/build_missing_data_report.ps1
   - regenerates the missing-data reports

For a full source-to-dashboard run in one step, use:

- tools/build_self_contained_dashboard.ps1
   - runs refresh from source inputs (without missing-data report)
   - writes dashboard_watchout_recommendations_embedded.html with updated embedded assets

## How to Validate Changes

### 1. Syntax and file validation

After editing tools/templates/dashboard_watchout_recommendations.template.html:

- check for diagnostics or syntax errors
- make sure no references remain to removed UI elements or old logic paths

### 2. Runtime dependency validation

Confirm the required runtime files still exist:

- dashboard_watchout_recommendations_embedded.html
- all required CSV and JSON inputs listed above

### 3. Case-based logic validation

Use known market-model-drivetrain examples to verify that:

- watchout detection matches the heatmap row
- duration logic matches the -3 markers
- prediction handling matches the current rule
- Cost per NVWR uses the correct lookup key and threshold
- recommendation text matches the expected node outcome

### 4. Export validation

Generate fresh exports from the dashboard after logic changes.

Do not rely on old CSV exports in the workspace after a rules update.

## Exact Update Sequence Used in Practice

When updating the dashboard, the working sequence is:

1. Identify the affected rule or UI area.
2. Read the local code path in tools/templates/dashboard_watchout_recommendations.template.html.
3. Make the smallest focused change in the owning function or markup.
4. Validate immediately after the edit.
5. Trace one or more real examples from the source data if behavior is questioned.
6. Update supporting documentation when the behavior or UI has changed.
7. Rebuild dashboard_watchout_recommendations_embedded.html.
8. Re-generate exports only after the runtime logic is confirmed.

## Important Constraints

1. The dashboard resolves data files from the repository root at runtime (relative project paths), so no machine-specific absolute paths are required.
2. Runtime behavior depends on the presence of generated JSON lookup files.
3. Old exported CSV files can become stale after any rules change.
4. Documentation should be updated whenever UI labels or business logic are changed.

---

## Recommended Maintenance Checklist

1. Update the HTML logic or UI.
2. Validate syntax and references.
3. Verify a few known business cases.
4. Regenerate any required derived files.
5. Generate fresh dashboard exports.
6. Update the documentation files.
